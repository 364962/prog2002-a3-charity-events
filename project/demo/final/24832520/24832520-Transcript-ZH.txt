1. 项目范围与个人讲解重点 [00:00]

这是鲁彧的 Good Together 第三次作业讲解，学号为 24832520。
我的讲解重点是数据库、接口、数据一致性和部署。
这些主题对应项目账户下记录的数据库结构、后端、启动入口和部署提交。
应用把公开的慈善活动网站和独立的管理网站，连接到同一个 Express 服务和 MySQL 数据库。
接下来我会结合搜索、报名和后台管理流程解释实现方式，再展示已验证的 SCU 部署。
演示使用虚构的报名者信息，不处理在线支付。

2. 数据库关系与约束 [00:39]

数据库包含四张表：组织、分类、活动和报名。
一个组织可以举办多个活动，一个分类可以关联多个活动，每条报名记录只属于一个活动。
报名表保存联系方式、票数、报名时间，以及报名时的单价快照。
活动编号和邮箱组成的联合唯一键，防止同一活动重复报名，同时允许同一人参加其他活动。
限制删除的外键防止删除已有报名的活动，数据库触发器还会检查数值是否合法。
初始数据包含两个组织、六个分类、十二个活动和十二条报名，并包含已结束及暂停发布的示例。

3. 搜索接口与参数绑定 [01:22]

公开活动接口返回尚未结束且正常发布的活动，并按开始时间和编号排序。
搜索支持开始日期、地区和分类，提交的筛选条件通过 AND 组合。
例如，在已部署的网站中选择 Southport 和趣味跑分类，会得到对应的海岸跑步活动。
接口先验证查询参数，再通过参数占位符把用户输入与 SQL 语句分开传入。
地区筛选还会转义通配符，避免把用户输入误当作通配模式。
非法编号或日期会返回验证错误，合法但没有匹配结果的搜索则返回空列表。

4. 报名事务与并发控制 [02:05]

报名接口先验证活动编号和请求内容，然后开启数据库事务。
它使用 FOR UPDATE 锁定活动行，再检查活动是否正常发布且尚未结束。
服务端从被锁定的活动行读取票价，并自行生成报名时间，不信任浏览器传来的价格。
活动修改和删除使用同一行锁，使报名与改价、暂停发布和删除操作保持一致。
事务成功后返回保存的记录和 201 状态码，失败时先回滚，再释放数据库连接。
即使两个相同的请求几乎同时到达，唯一键仍是阻止重复报名的最终保障。

5. 从接口响应到页面内容 [02:48]

在浏览器中，搜索表单生成网址参数，再通过共享的 JSON 请求函数调用 fetch。
服务端返回 data 数组，renderEvents 根据数组生成可见的活动卡片。
数据库文本通过 textContent 写入，而不是作为可执行的 HTML 插入，活动图片也限制为本地资源路径。
请求期间页面显示加载状态，失败时给出错误和重试操作，避免只留下空白结果。
报名使用相反方向的数据流：表单发送 JSON，再显示服务端返回的编号和总金额。
刷新活动页面后会重新取得已保存的报名，这证明数据存在数据库中，而不是浏览器里的临时变化。

6. 管理规则与删除保护 [03:37]

管理端活动列表包含正常发布、已结束和暂停发布的记录，与公开列表的范围不同。
创建活动使用 POST，修改使用 PUT，删除使用 DELETE，每次写入都经过服务端验证。
录制的操作流程创建一个临时活动，保存暂停发布的修改，再经确认删除没有报名的记录。
当活动已有报名时，删除会返回冲突，界面提示可以改为暂停发布。
当活动仍引用某个分类时，该分类同样不能删除，以保护数据库关系。
公开报名列表不显示邮箱和电话，管理端会显示这些信息，但此教学版本没有管理端身份验证。

7. 天气功能与验证证据 [04:22]

可选的天气服务根据活动坐标和布里斯班时区，向 Open Meteo 请求预报。
它设置了超时和缓存，并在缺少坐标、网络失败或日期超出预报范围时给出清晰说明。
本地通过了七十一项后端测试，覆盖重复报名、受保护的删除、并发操作和数据库约束。
Chromium 和 WebKit 中通过了四十六项浏览器检查，包含手机、平板和桌面布局。
本地后端测试也在 Node 十八点二十点八版本通过，与 SCU 提供的运行环境一致。
这些日志记录了具体检查及日期，并不表示已经测试了所有可能的生产场景。

8. SCU 部署与技术总结 [05:07]

我的 SCU 部署地址显示在画面上，管理网站位于 admin 路径。
应用位于私有目录，通过 app.js 在 Passenger 生产模式下启动，并使用专用 MySQL 数据库。
数据库凭据只保存在主机中，配置文件、SQL 和依赖不会作为网站文件公开。
十月十一日，该站点通过十四项 HTTPS 检查和九项外部浏览器检查，包括使用虚构信息实际报名并刷新确认。
四十个部署文件的校验值全部匹配，临时验收记录已经清理，原始示例数据得到保留。
核心设计是由数据库和接口保证数据完整性，再由浏览器清晰、及时地展示每一步结果。
